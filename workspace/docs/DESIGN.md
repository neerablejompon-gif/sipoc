# RMIC Workspace — การวิเคราะห์ ออกแบบ และข้อเสนอแนะ

ระบบรวม **ระบบมอบหมายและติดตามงาน กบค.** (Apps Script เดิม) กับ **ระบบติดตามผล SIPOC** และเพิ่มการรายงาน **SEAM / CBE**
ไว้ในเว็บแอปเดียว ใช้ Google Sheets เป็นฐานข้อมูลเหมือนเดิม แต่ย้ายส่วนประมวลผลจาก Google Apps Script ไป **Google Cloud Run**
และให้ **Cloudflare** เป็นด่านหน้า (โดเมน, WAF, cache)

---

## 1. สถาปัตยกรรม

```
ผู้ใช้ (เบราว์เซอร์ / มือถือ)
   │ https://rmic.<โดเมนของกอง>
   ▼
Cloudflare ── DNS · TLS · WAF/DDoS · Rate limit · (ตัวเลือก) Cloudflare Access
   │ Worker ส่งต่อ + header X-Origin-Secret · cache ไฟล์ static ที่ edge
   ▼
Google Cloud Run  (Node.js 22 + Express, max 1 instance, scale-to-zero)
   ├─ /            หน้าเว็บ SPA (HTML/CSS/JS ไม่ต้อง build)
   ├─ /api/*       REST API — ตรวจ session + บทบาทที่ server ทุกคำขอ
   └─ Google APIs  ผ่าน service account หรือ OAuth ของบัญชีระบบ
        ├─ Sheets API ─► สเปรดชีตงาน (Tasks_DB 70, Tasks_DB, Staff_List, ActionPlanDATA, Task_Log, External_Links, Reports_Log)
        │              ─► สเปรดชีต SIPOC (sipoc-seed, Tracking, Attachments, Log, SEAM_Topics, SEAM_Reports)
        ├─ Drive API  ─► โฟลเดอร์ไฟล์แนบ / หลักฐาน / รายงาน
        └─ Docs API   ─► template ทม.13 (เมื่อตั้งค่า)
   LINE Messaging API ◄─ แจ้งเตือนงานใหม่ / ส่งงาน / ผลพิจารณา (best-effort)
```

**เหตุผลที่เลือก**

| ทางเลือก | เหตุผล |
|---|---|
| Cloud Run แทน Apps Script | ไม่มีโควตา 6 นาที/การเรียก, ตอบเร็วกว่า (ไม่มี cold start ของ HtmlService), ใช้ git/CI/test ได้จริง, คุมความปลอดภัยและ header ได้, จ่ายตามใช้ (ผู้ใช้ ~10 คน อยู่ใน free tier) |
| ยังใช้ Google Sheets | ทีมแก้ข้อมูลในชีตได้เหมือนเดิม, ระบบ Apps Script เดิมยังอ่าน/เขียนชีตเดียวกันได้ระหว่างเปลี่ยนผ่าน |
| Cloudflare Worker เป็น proxy | ใช้โดเมนของกองได้ทุก region ของ Cloud Run, ได้ WAF/rate limit ฟรี, ปิดการเข้าตรงที่ URL ของ Cloud Run ด้วย shared secret |
| Vanilla JS (ES modules) | โค้ดอ่านง่าย ไม่ต้อง build, เหมือนแนวทางของระบบ SIPOC เดิมใน repo นี้, Chart.js เก็บในโปรเจกต์ (ไม่พึ่ง CDN) |
| max-instances = 1 | การเขียนชีตใช้ lock ในโปรเซสเพื่อกันข้อมูลชนกัน (แทน `LockService`) — พอสำหรับ ~10 คน ถ้าโตขึ้นค่อยย้ายตารางงานไป Firestore/Cloud SQL |

## 3. Workflow งาน และ Task Tracking

```
มอบหมาย ──► ดำเนินการ ──► ส่งงาน / รอเห็นชอบ (หผ.) ──► เห็นชอบแล้ว / รออนุมัติ (หก.) ──► อนุมัติแล้ว
 Assigned    In Progress    Pending Manager Approval      Pending Director Approval         Completed
                 ▲                    │ ส่งกลับ (ต้องมีเหตุผล)        │ ส่งกลับ
                 └──────── Needs Revision ◄────────────────────────┘
```

| กฎ | รายละเอียด |
|---|---|
| ผู้ส่งงาน | เฉพาะผู้รับผิดชอบ (หรือ Admin) · ส่งได้จาก Assigned / In Progress / Needs Revision |

## 4. ข้อมูล (ไม่ย้ายฐานข้อมูล ไม่ลบ/ย้ายคอลัมน์เดิม)

**Tasks_DB 70** — เพิ่มคอลัมน์ต่อท้ายอัตโนมัติเมื่อเขียนครั้งแรก:
`SipocId, PlanRef, AssignedBy, ReportText, Attachments (JSON หลายไฟล์), SubmittedAt, ApprovedAt, UpdatedAt`
คอลัมน์เดิม (`DueDate`, `Summit date`, `AttachmentURL`, `Status` …) ยังเขียนคู่ขนาน ระบบเดิมจึงอ่านข้อมูลใหม่ได้

**ชีตใหม่ที่ระบบสร้างเอง:** `Task_Log`, `External_Links`, `Reports_Log` (สเปรดชีตงาน) · `SEAM_Topics`, `SEAM_Reports` (สเปรดชีต SEAM — ตอนนี้ใช้สเปรดชีต SIPOC จนกว่าจะได้ฐานข้อมูลจริง)

**ปีงบประมาณ:** `TASKS_SHEET` = ชีตปีปัจจุบัน (เขียนได้), `TASKS_ARCHIVE_SHEETS` = ชีตปีก่อน (อ่านอย่างเดียว แสดงใน My Task เมื่อเลือก "ทุกปี") — ถ้า TaskID ซ้ำกันใช้ข้อมูลชีตปีปัจจุบัน

**รหัสงานใหม่:** `RM70-0001` เรียงต่อเนื่อง ออกเลขภายใน lock (แทน `RM-` + เลขท้าย timestamp ที่อาจซ้ำ)

**แผนปฏิบัติการ (ActionPlanDATA):** หาแถวหัวจากข้อความ "กิจกรรม", "แผน/ผล", "ต.ค." (ไม่ hardcode เลขแถว/คอลัมน์) และรวมแถวแผน/ผลด้วยรหัสกิจกรรม (เช่น 3.2 ที่ชื่อแผนกับผลต่างปีกันยังรวมเป็นกิจกรรมเดียว)

**สถานะกิจกรรม (ใช้ร่วมทุก Dashboard):** เสร็จสิ้น = มีผลครบทุกเดือนตามแผน · ล่าช้า = เดือนตามแผนที่ผ่านไปแล้วมีผลไม่ครบ · ต้องเร่ง = เดือนนี้อยู่ในแผนแต่ยังไม่มีผล · ยังไม่ถึงกำหนด · ตามแผน

## 5. Team Performance (ข้อเสนอการประเมิน)

ประเมิน **รายคนรายเดือน** จากงานที่ครบกำหนดในเดือนนั้น (ไม่นับงานยกเลิก และงานที่ยังไม่ถึงกำหนดและยังไม่ส่ง)

| ตัวชี้วัด | สูตร | น้ำหนัก |
|---|---|---|
| อัตราส่งงาน | งานที่ส่งแล้ว ÷ งานทั้งหมดของเดือน | 50% |
| อัตราทันกำหนด | ส่งภายในวันครบกำหนด ÷ งานที่ส่ง | 30% |
| คุณภาพ | 1 − (งานที่เคยถูกส่งกลับ ÷ งานที่ส่ง) | 20% |

เกรด A ≥ 85 · B ≥ 70 · C ≥ 55 · D < 55 · แสดงแนวโน้ม 6 เดือน (sparkline)
**หัวหน้าแผนก/หัวหน้ากอง** ถูกประเมินด้วยสูตรเดียวกันจากงานของตนเอง และมีตัวชี้วัดเสริม: จำนวนงานที่พิจารณา + **เวลาพิจารณาเฉลี่ย (เป้าหมาย ≤ 2 วัน)** ซึ่งเป็นคอขวดหลักของระบบเดิม
สิทธิ์: หผ. เห็นทีมตนเอง · หก./แอดมิน เห็นทุกคน · ข้อเสนอเพิ่ม: เมื่อข้อมูลครบ 1 ไตรมาสควรทบทวนน้ำหนักร่วมกับทีม และอาจเพิ่มคะแนนความยากของงาน (Priority/Urgency) เป็นตัวคูณ

## 6. ความปลอดภัย

| ปัญหาในระบบเดิม | การแก้ในระบบใหม่ |
|---|---|
| ตรวจรหัสผ่านที่ฝั่งเบราว์เซอร์ รหัสผ่านเดาได้ง่ายและฝังอยู่ในโค้ดหน้าเว็บ | ตรวจที่ server เท่านั้น, session เป็น signed httpOnly cookie, จำกัดการเดา 5 ครั้ง/15 นาที, รองรับ hash แบบ scrypt (`npm run hash-password`), ผู้ใช้เปลี่ยนรหัสผ่านเองได้ |
| LINE Channel Access Token อยู่ในโค้ด | อ่านจาก Secret Manager เท่านั้น — **ควร Reissue token ตัวเดิมทันที** เพราะเคยเผยแพร่ในโค้ด |
| สิทธิ์อนุมัติเชื่อชื่อที่ client ส่งมา | บทบาทมาจาก Staff_List ที่ server ทุกคำขอ |
| `getTasks()` เขียนสถานะทับชีต | อ่านอย่างเดียว คำนวณเลยกำหนดตอนอ่าน |
| ไม่มี lock / TaskID ซ้ำได้ | lock ต่อสเปรดชีต + เลขงานต่อเนื่อง |
| `innerHTML` กับข้อมูลชีต | escape ทุกค่า, CSP ห้าม inline script |
| อัปโหลดไม่จำกัด | ≤ 15 MB, allowlist ชนิดไฟล์, ตรวจสิทธิ์ก่อนอัปโหลด, ดาวน์โหลดได้เฉพาะไฟล์ที่อ้างอิงในระบบ |
| — | กัน CSRF ด้วย header, ลิงก์ภายนอกรับเฉพาะ `https://`, Cloud Run รับเฉพาะคำขอจาก Cloudflare (shared secret) |

## 7. ข้อเสนอแนะ

1. **ความปลอดภัยก่อนเปิดใช้:** Reissue LINE token, ตั้งรหัสผ่านใหม่ให้ทุกคนผ่านหน้า "ตั้งค่าระบบ" (เก็บเป็น hash), เปิด **Cloudflare Access** (ฟรี ≤ 50 คน) ให้ยืนยันอีเมลด้วย OTP ก่อนเข้าถึงหน้าเว็บอีกชั้น
2. **ยืนยันชีตปีปัจจุบัน:** ตอนนี้ `Tasks_DB` และ `Tasks_DB 70` มีข้อมูลเหมือนกัน (838 แถว) — ตั้งค่าเริ่มต้นให้ `Tasks_DB 70` เป็นปีปัจจุบันและ `Tasks_DB` เป็นปีก่อน ถ้าตั้งใจกลับกันแก้ที่ env ได้ทันที · แนะนำล้างงานปีก่อนออกจาก `Tasks_DB 70` เพื่อให้ตัวเลขปีนี้ถูกต้อง
3. **ลดคอขวดการอนุมัติ:** ใช้หน้าอนุมัติแบบเลือกหลายรายการ + ตัวจับเวลา "รอ n วัน" · ขั้นต่อไปแนะนำ LINE แจ้งเตือนรายวัน (08:00) และเตือนงานที่รอพิจารณาเกิน 2 วัน (Cloud Scheduler เรียก endpoint)
4. **ผูกงานกับ SIPOC ตอนมอบหมาย:** เพื่อให้ผลงานรายวันกลายเป็นผล SIPOC/SE-AM อัตโนมัติ ไม่ต้องกรอกซ้ำ
5. **ให้ทุกคนมีอีเมลของตนเองใน Staff_List** (ตอนนี้ใช้อีเมลเดียวกัน) แล้วเปลี่ยนเป็นเข้าสู่ระบบด้วยบัญชี Google (Sign in with Google) ในระยะถัดไป
6. **ทำความสะอาดข้อมูล:** Priority มีหลายค่าปน (Medium/สูง/High) — ระบบอ่านได้ทุกแบบแล้ว แต่ควรใช้ภาษาไทยชุดเดียวต่อจากนี้
7. **สำรองข้อมูล:** ตั้ง Apps Script เล็ก ๆ หรือ Cloud Scheduler สำเนาสเปรดชีตรายสัปดาห์
8. **ช่วงเปลี่ยนผ่าน:** เปิดระบบเดิมแบบอ่านอย่างเดียว 2–4 สัปดาห์ (ทั้งสองระบบใช้ชีตเดียวกันได้) แล้วปิด deployment เดิม
9. **ขยายระบบ:** ถ้าผู้ใช้หรือข้อมูลเพิ่มมาก (> 5,000 งาน หรือ > 30 คนพร้อมกัน) ย้ายตารางงาน/Log ไป Firestore แล้วเปิด Cloud Run หลาย instance
